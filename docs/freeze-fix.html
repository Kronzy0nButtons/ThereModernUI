Taming the 8 second freeze

Why the client rubberbands on Windows 11, and what ThereModernUI does about it

If you have played There on Windows 11 since September, you know the feeling: you teleport somewhere, or a message comes in, and the whole world locks up. Your avatar rubberbands, chat stalls, and roughly eight seconds later everything snaps back as if nothing happened.

This is not your PC and it is not your connection. The There team investigated it and published what they found. In their own words:

"Something in the Windows 11 update causes these Edge components to freeze for 8 seconds whenever There Edge requests a file - a HTML file, an image, Javascript, etc. [...] When the Edge component freezes it also causes the There 3D client to freeze, which results in the rubberbanding." There.com, official changelog

Their advice while waiting on Microsoft was to keep the MessageBar, ChangeMe, Compass and FunFinder closed, with the warning that every teleport and MessageBar update opens one of those windows anyway. In other words: the only known workaround was to not use the UI.

ThereModernUI 1.0.6 made this noticeably better, and 1.0.7 goes further. Not by waiting for Microsoft, but by changing how those windows load their files, and how often they ask the game for anything at all. Here is the full story, including what it can and can't do.

How the UI windows actually work

When Flash died, the There team rebuilt the old Flash controls as small embedded browser windows, a system they call There Edge. Each control, the Compass, the MessageBar, ChangeMe, FunFinder, the teleport screen, is a little web page running inside a Microsoft Edge (WebView2) window that floats over the game. The component that hosts all of those windows is a file in your There folder called FlashProxy.dll, and the There team generously published its source code as open source.

That last part matters, because ThereModernUI already rebuilds that component from source to power its own features. The same windows that run the ModernUI dock also run the stock controls. So when the freeze bug appeared, we were in an unusual position: we ship the exact piece of the client where the bug lives.

What actually freezes, and why it takes the world with it

A game client has a main thread: one worker that runs the simulation, pumps messages, and draws the world, over and over, many times a second. Anything that runs on that thread stops the world while it runs. That is fine when everything on it is fast.

Here is the catch we found in the There Edge source. Every file one of those UI windows requests, its page, its scripts, its images, its sounds, is intercepted by the host and fetched through an old piece of Windows plumbing called URLMon, and that fetch runs on the game's main thread. Picture a cashier who personally walks to the warehouse for every single item: the queue stands still until they come back.

For years that was harmless, because the warehouse was fast. Then a Windows 11 update made that plumbing stall. Now every trip can take about eight seconds, and the game stands in that queue every time. That explains everything the There team observed:

  • Why a UI window freezes the 3D world: the world and the file fetch share the same thread.
  • Why keeping windows closed helps: closed windows request no files.
  • Why every teleport freezes: teleporting opens the slideshow window, which loads its files.
  • Why it is worst on fresh content: files already in the browser cache never reach the slow path, new ones always do.

The fix: never make the game wait for a file

ThereModernUI's rebuilt FlashProxy.dll adds what we call the file lane. When a UI window asks for a static file, a page, a script, an image, a font, a sound, the request is handed to a background worker thread. The game's main thread moves on immediately. When the file is ready, the worker hands it back and the window carries on loading.

The file lane does two things at once:

  • It disconnects the freeze from the game. Even if Windows stalls a fetch, it stalls a background helper. The simulation never stands in that queue again, so the world cannot rubberband because of it.
  • It skips the broken plumbing entirely. Those static files are ordinary files on disk, sitting right next to the client. The worker reads them directly instead of going through URLMon at all, so loads are not just non-blocking, they are faster.

And because everything the devs listed, Compass, MessageBar, ChangeMe, FunFinder, plus the teleport slideshow, runs inside the one component we rebuild, the fix covers all of them. Including the stock windows ModernUI does not reskin.

Going further in 1.0.7

The file lane took the biggest freeze away, but it still started on the game's thread: every file request arrived there first and was handed off from there. And files were only one kind of request. 1.0.7 goes after the rest.

The dock's own files skip the game entirely

WebView2 can serve a folder on disk by itself, under a private web address, without asking its host about each file. ModernUI's FlashProxy now maps two folders this way: the client's own folder (pages, scripts, map pictures, icons) and the picture store. The dock loads everything it can from those addresses, so its files never raise a request on the game's thread at all, not even for a moment. The file lane is still there for the stock windows, which ask for their files the old way.

Photos are downloaded once, ever

Clothing and item photos used to be fetched again whenever the browser cache forgot them. They are now kept in a picture store on your PC, filled in the background after you log in. Public pages from There's website (the shop, auctions, events) come through WinHTTP, a separate Windows network stack the game does not use, so a burst of them cannot hold up the game's own connections. Pages that need your login still go the game's way, because your session only lives there.

A queue for requests to the game

There is one more kind of request, and the file lane cannot help with it. When the dock needs something only the game knows (an item's actions, a menu, your inventory, who is nearby) it has to ask the client, and the client answers on its main thread. One question is quick. Fifty at once, which is what opening a full Inventory or Wardrobe used to fire, add up to a stall you can feel.

So in 1.0.7 every question to the game goes through a queue. Only a few run at once, with a short gap between them, and the rest wait their turn. A request that hangs is dropped after 15 seconds instead of blocking the line. Live readings that have to stay smooth (your position for the map and speedometer, the people around you) skip the queue, and so do the dock's own files.

When a lot is waiting, a slim bar above the dock says Waiting for the There client to catch up, so a panel that fills in gradually is explained rather than looking stuck.

You choose the pace

How many questions run at once is up to you, in Settings > Sync & data > Requests to the game, from 1 to 4. The default is 2.

  • Fewer at once is smoother: the game is never asked more than it can answer between frames, but big panels take longer to fill.
  • More at once loads faster, at the cost of the odd hitch while a big panel loads. On a fast PC that may not be noticeable at all.

Every PC and every install is different, so try a setting, open your Inventory and Wardrobe, and keep the one that feels best.

The evidence

None of this is guesswork. There Edge is open source, so the whole chain can be read, and the built files can be checked.

The stock code fetches every file through URLMon. In the original There Edge source, the request handler in FlashProxy.cpp hands each file straight to FlashRequestProxy::Init, which does this:

bindHost->CreateMoniker(uri, this, &moniker, 0);
moniker->BindToStorage(this, nullptr, IID_IStream, (void**)&m_stream);

Bind hosts and monikers are URLMon, the old Windows download machinery. The handler is registered with WebView2's add_WebResourceRequested, and WebView2 always runs those handlers on the thread that created the window: the game's own thread. There is no other thread it could use, because the stock source never creates one. The word CreateThread does not appear in it.

Our code hands files to a worker and returns. In ModernUI's build, the same handler first offers each static file to the file lane. That holds the request open, queues it for a worker thread and returns straight away. The worker reads the file with plain CreateFile and ReadFile calls and posts the result back when it is done.

The shipped DLL really contains it. Comparing the functions each DLL uses from Windows:

FlashProxy.dllThread and file functions it uses
Stock There Edgenone
ThereModernUICreateThread, CreateFileW, ReadFile, SetEvent, CreateEventW, PostMessageW

Anyone can repeat this with Microsoft's dumpbin /imports on the two files.

What deliberately did not change

Game data and commands, chat, presence, inventory, everything the windows say to the client, still travel their original route. That route carries information about which window is asking, and the client checks it, so we leave it alone. The file lane touches files and nothing else, and the queue only changes when the dock's questions are sent, not how.

It is also built to fail safe. If a requested file is not on disk where expected, the request quietly falls back to the original path and behaves exactly like the stock client. And if you ever want the stock behaviour back entirely, set the environment variable TMUI_FILELANE=0 and restart There.

What to expect

Play is noticeably smoother: teleports, messages and the dock's panels no longer hold the world up while their files load, and big panels fill in at a pace the game can keep up with. You will still catch the odd stutter here and there. That's expected. There's client is from a different era of PC software, with a modern WebView2 now sitting on top of it, and plenty of its own work still runs on that one main thread. ModernUI takes away the biggest, most regular causes of freezing, not every pause the client can have. If panels feel slow or the game feels jumpy, the Requests to the game setting is the dial to turn.

To be fair to Microsoft and to There: the underlying Windows bug is real and still exists, and it is not There's code that broke. What ModernUI changes is where the slow work happens, so it can no longer hold up the game. If Microsoft ships a fix, nothing here gets in its way.

And this isn't the end of it. As we keep working to modernize the There client with what's available to us, we'll always look for ways to improve the experience where we can.

Try it

Install ThereModernUI, then do the things that used to hurt: teleport a few times in a row, let messages come in, open FunFinder. You should notice far fewer freezes.
